# Spektral performance benchmarks

Spektral uses five complementary benchmark suites. Do not combine their numbers: each suite
answers a different optimization question.

## Commands

| Suite                   | Run                                              | Check baseline                          | Create baseline                            |
| ----------------------- | ------------------------------------------------ | --------------------------------------- | ------------------------------------------ |
| CPU core                | `pnpm run perf:spektral:core`                    | `pnpm run perf:spektral:core:check`     | `pnpm run perf:spektral:core:baseline`     |
| Compute topology paired | `pnpm run perf:spektral:compute-topology:paired` | —                                       | —                                          |
| Browser runtime         | `pnpm run perf:spektral`                         | `pnpm run perf:spektral:check`          | `pnpm run perf:spektral:baseline`          |
| Hardware GPU            | `pnpm run perf:spektral:gpu`                     | `pnpm run perf:spektral:gpu:check`      | `pnpm run perf:spektral:gpu:baseline`      |
| Real renderer           | `pnpm run perf:spektral:renderer`                | `pnpm run perf:spektral:renderer:check` | `pnpm run perf:spektral:renderer:baseline` |

The commands above run from the repository root. Inside `packages/spektral`, use `perf:core`,
`perf:runtime`, `perf:gpu`, or `perf:renderer` and the matching suffix. Use the `:headed` command to
diagnose a hardware suite in a visible browser.

## CPU core suite

`perf:core` isolates deterministic CPU hot paths:

- material resolution, including a material with 64 `vec4f` uniforms;
- checked packing, fast packing, dirty-range detection, and the composite renderer uniform path;
- render graph planning and render target resolution;
- scheduler execution with profiling disabled and enabled;
- compute storage bind-group cache hits.

Use this suite when changing material normalization, uniform handling, graph planning, scheduling, or
resource caches. Its baseline is `benchmarks/baselines/core.json`.

## Compute topology paired A/B

`perf:spektral:compute-topology:paired` runs the legacy defensive resource-copy/resolution path and
the renderer-owned static-topology cache through the same worker. The fixed release-evidence command
uses 12 fresh processes per arm, four external buffer resources per pass, scenarios 0/4/16/32,
balanced alternating arm order, shuffled scenario order, raw samples, and validated checksums:

```sh
pnpm run perf:spektral:compute-topology:paired
```

The exact package-level equivalent is:

```sh
pnpm --dir packages/spektral run perf:compute-topology:paired
```

Both aliases expand to `--runs=12 --seed=1394060030`. The tracked result and acceptance contract are
recorded in `benchmarks/compute-topology-paired-evidence.md`; raw samples remain in the ignored
`benchmarks/results/compute-topology-paired-latest.json`.

The tracked CPU baselines are local release gates for the recorded environment, not universal
performance targets. A strict comparison requires the same Node, V8, pnpm, OS, CPU, power mode,
configuration, and suite hash. If the suite hash changes, archive the old baseline and capture a new
one under controlled conditions instead of comparing unrelated workloads.

## Browser runtime suite

`perf:runtime` runs the dedicated `?scenario=perf` application in Chromium with SwiftShader. It
measures browser/runtime behavior, not hardware shader speed:

- navigation to the first rendered frame;
- scheduler and render invocation rates for `always`, `on-demand`, and `manual` modes;
- p50, p95, and maximum latency of individual manual `advance()` calls;
- compute storage bind-group creation pressure over 1,000 synthetic frames.

Use this suite when changing lifecycle, scheduling, adapters, or submission behavior. SwiftShader
keeps semantics reproducible, but RAF and software rasterization make its frame rate unsuitable for
judging real shaders. Its baseline is `benchmarks/baselines/runtime.json`.

## Hardware GPU suite

`perf:gpu` launches Chromium with hardware WebGPU, requires `timestamp-query`, and rejects fallback,
CPU, SwiftShader, llvmpipe, and null adapters. It reports the adapter, backend, driver, browser
version, and a fingerprint before printing results.

Every full run starts five fresh Chromium processes and requests a new WebGPU adapter and device in
each process. The suite exercises WGSL generated by Spektral's material and compute shader builders:

- baseline fragment cost at 1024×1024;
- 96-iteration fragment ALU load at 512², 1024², and 2048²;
- nine-sample texture filtering at 1024²;
- linear-to-sRGB output conversion and `rgba16float` render targets;
- a 64 MiB read-modify-write compute workload;
- a 128-iteration compute ALU workload;
- cold pipeline compilation in each fresh process and warm compilation on the same device.

GPU execution uses timestamp queries, not RAF or JavaScript wall time. Each render sample starts from
the end timestamp of a real 1×1 marker pass and ends at the end of the measured pass. A pixel from
both targets is copied after the timestamps so the driver cannot discard the work. Compute samples
use beginning/end pass timestamps.

The report separates three phases:

- cold browser startup and WebGPU device acquisition;
- cold and warm pipeline compilation;
- steady GPU execution after workload warmup.

Each process keeps its raw compile and GPU samples. Aggregates include pooled samples and the
distribution of independent run medians. Strict comparisons use the median of run medians for warm
pipeline and steady GPU metrics. Cold startup, device acquisition, and first compilation use one
sample per fresh process, so a slow first run cannot disappear inside warm samples.

The ALU resolution curve is especially useful: a ratio near 4× when each dimension doubles confirms
a pixel/shader-bound workload. The baseline fragment is subtracted from ALU, texture, and sRGB
results to expose their approximate incremental cost. Values close to the marker floor should be
treated as indistinguishable.

### Hardware baselines

Hardware results are comparable only when the CPU, GPU, backend, driver, macOS release, architecture,
power mode, Chromium channel and major version, and suite hash match. Chromium patch releases may
differ. The suite writes one immutable baseline per fingerprint to
`benchmarks/baselines/<adapter>-<fingerprint>.json`.

Create a baseline on the reference machine:

```sh
SPEKTRAL_PERF_POWER_MODE=ac-high-power pnpm run perf:spektral:gpu:baseline
pnpm run perf:spektral:gpu:check
```

Baseline creation requires a clean worktree, controlled power mode, and at least five fresh browser
processes. It refuses to overwrite an existing fingerprint. The strict check also requires at least
five processes and fails on a missing metric, old schema, or incompatible environment. It never
updates a baseline.

A regression must exceed both its relative threshold and its absolute noise floor. Pipeline
compilation and cold startup use wider thresholds than steady GPU timing because browser and driver
caches add more variance. Cold process, device, and first-compilation metrics remain part of the
gate.

Set `SPEKTRAL_PERF_BROWSER_CHANNEL` to compare another installed Chromium channel. Never compare
its result with a baseline generated by a different channel or fingerprint.

## Real renderer suite

`perf:renderer` runs Spektral's production-built `createRenderer` path on a physical GPU. It rejects
software and fallback adapters and requires `timestamp-query`. The suite launches five fresh browser
processes by default and exercises 512×512 no-pass, 16 `ShaderPass`, and storage-buffer
`ComputePass` scenarios.

It records three distinct intervals:

- amortized JavaScript time spent in `renderer.render()` as CPU submit cost;
- GPU completion span from the end of a marker queued before `renderer.render()` to the beginning of
  a marker queued after it;
- wall time from immediately before `renderer.render()` to `queue.onSubmittedWorkDone()`.

Every browser run keeps raw samples. The aggregate contains both pooled samples and a distribution of
independent run medians with a bootstrap confidence interval. Use the run-median distribution for
comparisons; pooled p95/p99 reveal long-tail behavior but are not independent samples.

The untimed correctness sink copies the renderer's actual canvas texture before presentation, checks
a full-frame checksum, alpha coverage, and RGB range before and after the timed batches, and verifies
that the compute storage sentinel advances. The readback is deliberately outside timing windows.

The strict check compares the median of independent run medians. It rejects baselines with fewer than
five processes, a different scenario or correctness contract, an old schema, or an incompatible
hardware fingerprint. CPU submit, queue completion, and GPU frame spans each have a relative limit
and an absolute noise floor.

Do not create a baseline from a one-off diagnostic run. Baseline creation requires a clean worktree,
at least five fresh browser processes, and an explicitly controlled power mode:

```sh
SPEKTRAL_PERF_POWER_MODE=ac-high-power pnpm run perf:spektral:renderer:baseline
pnpm run perf:spektral:renderer:check
```

`--runs=<n>` can shorten a local, non-strict diagnostic. Baseline creation and strict checks reject
fewer than five runs. A baseline is immutable: the command refuses to overwrite an existing
fingerprint. Archive the prior raw result before accepting a deliberate new baseline.

There is no GitHub-hosted hardware gate. These checks run only on the reference Apple M4 Pro because
hosted runners do not provide the required physical GPU and Metal environment.

Do not interpret SwiftShader runtime numbers as hardware throughput, and do not compare real-renderer
results across fingerprints. The fingerprint records the Apple M4 Pro CPU and adapter, Metal backend
and driver, macOS release, power mode, Chromium major version, and suite hash.

## Output files

Latest run files are ignored by Git:

- `benchmarks/results/core-latest.json`
- `benchmarks/results/runtime-latest.json`
- `benchmarks/results/gpu-latest.json`
- `benchmarks/results/real-renderer-latest.json`

Tracked baselines live in:

- `benchmarks/baselines/core.json`
- `benchmarks/baselines/runtime.json`
- `benchmarks/baselines/<adapter>-<fingerprint>.json`
- `benchmarks/baselines/<adapter>-real-renderer-<fingerprint>.json`

Historical schema-v2 CPU baselines remain in `core-schema-v2.json` and
`runtime-schema-v2.json`. The last schema-v3 baselines captured before the 0.17.0 benchmark-suite
change remain in `core-pre-0.17.0.json` and `runtime-pre-0.17.0.json`. Strict commands read only
`core.json` and `runtime.json`, which use the current suite hash.

The pre-0.17.2 real-renderer baseline is preserved in
`apple-m4-pro-real-renderer-551cc81c4a408878-pre-0.17.2.json`. The linear postprocessing fix in
0.17.2 changes the sixteen-pass image checksum from `1909554165` to `4212639533`; the no-pass and
compute checksums remain unchanged. The active baseline is recaptured for that corrected output.
Before the refresh, all nine timing metrics passed the original thresholds in a five-process run.
The hardware fingerprint, benchmark workload, and regression thresholds are unchanged.
